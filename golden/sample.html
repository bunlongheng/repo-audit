1 Wrap order creation and stock decrement in one transaction Architect Critical M
Where: src/controllers/orders.controller.ts:218
Why first: Two sequential writes with no transaction: an insert into orders followed by a stock decrement. A crash or a rejected decrement between them leaves a paid order with stock never reserved, and two concurrent buyers can both pass the availability check.
Fix: Move both writes inside a single prisma.$transaction, and make the decrement conditional (UPDATE ... WHERE stock >= qty) so the database, not the request handler, is what prevents overselling.

Where: src/routes/webhooks.ts:44
Why first: The raw webhook payload is written to the application log at info level. It carries customer email, billing address and the payment-method fingerprint, so PII lands in log storage that has a different retention policy and a much wider read audience than the database.
Fix: Log event.id and event.type only. If the body is needed for debugging, put it behind a flag that is off in production and redact customer and payment_method before writing.

Full summary
A conventional three-layer Express service - routes, controllers, repositories - with Prisma as the only data access path and Redis used purely as a cache aside. The layering is real and mostly respected, but the controller layer has absorbed business logic that belongs in services, and there is no transaction boundary anywhere in the write path, so invariants that span two tables are enforced by convention rather than by the database.
  • Every HTTP route is a thin binding: src/routes/orders.ts:12 maps the verb to a controller method and does nothing else, so routing can be read in one file.
  • All database access funnels through src/repositories/; no controller imports the Prisma client directly (src/repositories/order.repo.ts:1 is the only place new PrismaClient appears), which is what makes the data layer swappable at all.
  • The controller layer is where the design slips: src/controllers/orders.controller.ts is 902 lines and holds pricing, stock and fulfilment decisions that the empty src/services/ directory was clearly meant to own.
  • No transaction boundary exists in the codebase - grep -rn 'prisma.$transaction' src/ returns nothing - so any invariant spanning two tables (order + stock, refund + ledger) is only as strong as the ordering of two separate awaits.
  • Redis is a clean cache-aside at src/cache/product.cache.ts:22: read-through with a TTL, and every write path deletes the key rather than updating it, so a stale entry cannot outlive a change.
  • Error handling is centralised in one Express error middleware (src/middleware/error.ts:18) that maps a small set of domain errors to status codes - the single best structural decision in the repo.
  • The Stripe integration is the one place the layering is bypassed: src/routes/webhooks.ts:44 reads and writes the database directly from the route, with no controller or repository in between.

Good, Bad, Ugly

Good

  • One centralised error middleware (src/middleware/error.ts:18) maps domain errors to status codes, so the API's error shape is a deliberate design rather than an accident of which handler failed.
  • Every database call goes through src/repositories/ - new PrismaClient appears exactly once, at src/repositories/order.repo.ts:1 - which is what makes the data layer testable and swappable at all.
  • CI runs against a real postgres:16 service (.github/workflows/ci.yml:14) instead of a mock, so the integration tests exercise genuine SQL, genuine constraints and genuine migration state.
  • TypeScript strict mode is on and has never been turned off for a file (tsconfig.json:7, zero @ts-ignore in src/), which is rarer than it should be and is doing quiet work throughout.
  • Cache invalidation is correct by construction: every write path deletes the key rather than updating it (src/cache/product.cache.ts:41), so a stale entry cannot outlive a change.

Bad

  • scripts/seed-dev.js:12 connects with the production DATABASE_URL when NODE_ENV is unset, and the README tells new developers to run it before setting anything.
  • The Dockerfile installs devDependencies into the runtime image (Dockerfile:11), which is most of the 412 MB and every one of their advisories.
  • .env.example has been out of date since the Redis migration - it still names REDIS_HOST and REDIS_PORT, which nothing reads any more.
  • Two git-tracked files under .vscode/ carry one developer's absolute paths, so the workspace settings only work on their machine.

Ugly

  • src/controllers/orders.controller.ts is 902 lines with 11 handlers, sitting next to a src/services/ directory that holds exactly one file - the intent is visible and unfinished.
  • The same three-line catch block appears twelve times across the controllers, each logging slightly differently, while a central error middleware already exists to do it once.
  • A TODO at src/controllers/orders.controller.ts:511 reads 'remove before launch' and is dated 2024-03; the service launched two years ago.
  • prisma/migrations/ contains two migrations whose names describe the opposite of what they do (20250114_drop_index adds one), which makes the history unreadable at exactly the moment you need it.
Bottom line: A competent, conventionally structured Express + Postgres order service whose real ceiling is that every request path still goes through one 900-line controller layer with no transaction boundary, so correctness under concurrency is asserted in code review rather than enforced by the database.
